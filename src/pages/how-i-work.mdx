## Start with what matters

I ask what needs to change, who needs it, and what the first release should deliver. Then I decide what can wait.

At StoragePal, staff were blocked by tools they used every day. [I fixed those first](/work/storagepal/#start-where-staff-were-blocked).

## Keep complexity useful

I consider speed, data accuracy, recovery from failures, and maintenance costs. Each technical choice should solve a real problem.

Every SPS warehouse had internet. [Removing offline support](/work/sps/#remove-complexity-the-warehouse-does-not-need) left a smaller system to maintain, with sessions saved on the server.

## Use AI, own the result

<Potion id="how-i-work" />

Coding agents help me write code, investigate problems, and test changes. I remain responsible for priorities, architecture, code review, and releases.

For each change, I document the requirements and limits. I check the result with regression tests, static analysis, and browser or API tests. When a check misses a problem, I improve it. [A production postmortem shows how](/blog/2026/09/25/ravenclip-engineering/#postmortem-a-syntax-error-in-production).

## Follow through after release

I share decisions, progress, and problems so the team has the context to keep working. After release, I use errors, staff feedback, costs, and usage to decide what to improve.

At RavenClip, [paying customers changed the product’s direction](/work/ravenclip/#learn-from-the-people-who-pay). When the evidence changes, I change the plan.
