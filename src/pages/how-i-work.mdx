## Find what’s getting in the way

StoragePal was already running when I joined, and staff used the platform all day. The most useful first step wasn’t a new feature. It was the inventory and reservation screens that were slowing them down, so [I fixed those first](/work/storagepal/#start-where-staff-were-blocked).

I still start the same way: what needs to change, who is waiting on it, and what can wait.

## Leave out what we don’t need

I built offline support into SPS, then looked at where the app would actually run. Every warehouse had internet, so [I removed it](/work/sps/#remove-complexity-the-warehouse-does-not-need) before daily use began. Staff need a connection to save changes, and there’s far less sync code to look after.

Speed, data accuracy, recovery from failures, and the cost of maintaining the code all matter. A pattern has to solve a problem we actually have.

## Use AI, own the result

<Potion id="how-i-work" />

Coding agents help me write code, investigate problems, and test changes. Deciding what to build, how it fits together, and whether it is ready to ship stays with me.

Before a change, I write down the requirements and limits. Then I check the result with regression tests, static analysis, and browser or API tests. When a check misses a problem, I improve the check. [A production postmortem shows how](/blog/2026/09/25/ravenclip-engineering/#postmortem-a-syntax-error-in-production).

## Pay attention after launch

I expected RavenClip’s customers to be people running news channels. The first to pay were an agency, an AI consulting firm, and a coach. [Their needs changed what I built next](/work/ravenclip/#learn-from-the-people-who-pay).

At StoragePal, errors, staff feedback, costs, and real usage decide what I improve. When I bring in developers or testers, I share the decisions, progress, and problems so they can keep the work moving.
