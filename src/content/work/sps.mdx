## Connect the booking to the warehouse floor

Before SPS, staff sorted out booking differences over email, and item locations were not always recorded. SPS puts the whole flow on a phone.

I built SPS end to end, from first commit to production. I also maintain the StoragePal platform it connects to, so both sides of the integration are mine to keep working.

## Remove complexity the warehouse does not need

An earlier version worked offline. But every warehouse already had internet, and offline support was a lot of extra code to maintain.

<div class="post-principles not-prose">
  <div class="card post-before fx">
    <p class="eyebrow">Before: offline mode</p>
    <div class="post-before-lines" aria-hidden="true"><span></span><span></span><span></span><span></span><span></span><span></span></div>
    <p>Extra offline state to maintain, next to the main StoragePal platform.</p>
  </div>
  <div class="card post-after fx" style="--d:70ms">
    <p class="eyebrow">After: online only</p>
    <dl>
      <div><dt>Online</dt><dd>Scanning needs a connection</dd></div>
      <div><dt>Saved</dt><dd>Sessions live on the server and survive a reload</dd></div>
      <div><dt>Smaller</dt><dd>Much less code to maintain</dd></div>
    </dl>
    <p class="post-after-foot"><span>Removed before daily production use began.</span></p>
  </div>
</div>

The app does not queue offline writes. The result is a clear limit, and a much smaller system to maintain.

## Keep work moving across system boundaries

Each system owns its own data. Staff sometimes need to print a label before StoragePal approves a change, and SPS does not make them wait.
