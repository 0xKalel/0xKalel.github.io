## Connect the booking to the warehouse floor

Before SPS, staff handled discrepancies through email and item locations were not recorded consistently. I built the app to compare what arrives with the booking, record condition and location, and prepare returns for approval.

I built it end to end, from first commit to production. I also maintain the StoragePal platform it connects to, so the integration and the warehouse workflow are both part of my responsibility.

## Remove complexity the warehouse does not need

An earlier version supported offline inventory work. Every warehouse already had internet, while offline state added a substantial maintenance burden alongside the main StoragePal application.

I removed offline support before daily production use began. Scanning now requires a connection. Sessions live on the server and can resume after a reload, but the app does not queue offline writes. That is an explicit operating constraint and a smaller system to maintain.

## Make a retry understandable

In one production incident, completion succeeded on the server but the phone never received the response. Staff retried, received errors, and thought the scan could not be completed.

I changed a repeated completion from the same user to return the saved successful result without repeating its side effects. A regression test covers this behavior. It addresses both duplicate processing and the misleading experience after a lost response.

## Keep work moving across system boundaries

StoragePal owns orders and article identifiers. SPS owns scan sessions, photos, and bay history. Staff sometimes need to print a label before an approved change has returned from StoragePal.

SPS predicts the identifier so they can label and place the item immediately. After approval, it reconciles against StoragePal’s response. If the prediction is wrong, the item is flagged for relabelling. This trades waiting on the warehouse floor for correction work in the exceptional case.

## Check the behaviors that matter

Tests cover repeated completion, duplicate approval, rejected returns restoring locations, and cancelled bay sessions rolling back. Staff use also shaped one-tap verification, a less prominent Cancel button, and customer-name search that accepts either word order.

From 13 April to 25 September 2026, staff completed **{evidence.sps.sessions} scanning sessions**, including sessions on **all 120 weekdays**. The records include **{evidence.sps.verifications} item verifications** and **{evidence.sps.bayChanges} bay changes**, of which **{evidence.sps.bayMoves} were moves between bays**. Verification counts are workflow events, not distinct physical items.

There is no measured before-and-after time saving. These figures establish regular use rather than an efficiency percentage.
