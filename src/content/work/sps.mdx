## Connect the booking to the warehouse floor

Before SPS, staff sorted out booking differences over email, and item locations were not always recorded. I built the app that compares what arrives with the booking, records condition and location, and prepares returns for approval.

I built it end to end, from first commit to production. I also maintain the StoragePal platform it connects to, so the integration and the warehouse workflow are both mine to keep working.

## Remove complexity the warehouse does not need

An earlier version worked offline. But every warehouse already had internet, and offline state was a lot of extra code to maintain next to the main StoragePal platform.

I removed offline support before daily production use began. Scanning now needs a connection. Sessions live on the server and survive a page reload, but the app does not queue offline writes.

The result is a clear limit, and a much smaller system to maintain.

## Make a retry understandable

In one production incident, a completion succeeded on the server but the phone never got the response. Staff retried, got errors, and thought the scan had failed.

Now a repeated completion from the same user returns the saved result instead of running again. A regression test covers it.

One change fixed two problems: the double processing, and the confusing errors after a lost response.

## Keep work moving across system boundaries

StoragePal owns orders and article IDs. SPS owns scan sessions, photos, and bay history. Staff sometimes need to print a label before StoragePal has approved a change.

SPS predicts the ID so staff can label and place the item right away. After approval, it checks the prediction against StoragePal's answer. If the prediction was wrong, the item is flagged for a new label.

Staff keep moving, and the rare wrong guess becomes a small correction later.

## Check the behaviors that matter

Tests cover repeated completion, duplicate approval, rejected returns restoring locations, and cancelled bay sessions rolling back.

Daily use shaped the details: one-tap verification, a less prominent Cancel button, and name search that accepts either word order.

From 13 April to 25 September 2026, staff completed **{evidence.sps.sessions} scanning sessions**, with sessions on **all 120 weekdays**. The records include **{evidence.sps.verifications} item verifications** and **{evidence.sps.bayChanges} bay changes**, of which **{evidence.sps.bayMoves} were moves between bays**. These counts are workflow events, and they show steady daily use.
