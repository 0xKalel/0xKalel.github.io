I started RavenClip because I wanted an easier way to follow the news. It turns news into short videos and publishes them on a schedule, and I build and run it with Laravel, React, a Node/Skia renderer, and FFmpeg. The [case study](/work/ravenclip/) covers the product; this post covers the technical choices and their limits.

## Save progress so work can resume

Each stage saves its status in the database. After a failure, processing resumes from that point without repeating paid work. Voice and visuals are generated in parallel, then combined during rendering.

  <div class="card fx">
    <span class="post-icon"><Icon name="ph:lock-simple" aria-hidden="true" /></span>
    <h3>One worker per stage</h3>
    <p>A background process starts each stage when it is ready. A database row lock prevents two workers from starting the same stage.</p>

  <div class="card fx" style="--d:70ms">
    <span class="post-icon"><Icon name="ph:timer" aria-hidden="true" /></span>
    <h3>Ordered timeouts</h3>
    <p>The job times out first, then the supervisor, then the queue retries it. A stuck render reuses the assets already generated.</p>
  </div>
  <div class="card fx" style="--d:140ms">
    <span class="post-icon"><Icon name="ph:seal-check" aria-hidden="true" /></span>
    <h3>Publish once</h3>
    <p>Status checks and a unique database constraint prevent duplicate posts.</p>

Starting each stage as soon as the previous one finished reduced the median delay. The longest waits did not improve.

<div class="decision-note not-prose">
  <p class="eyebrow">When a simpler approach works</p>
  <p>Saving each stage adds code to maintain. After a user edits a scene, a simple job chain handles the short rebuild. The full recovery system is for automatic generation and publishing.</p>
</div>

## Structure AI output and check it

Each model returns structured output that is checked against a schema. Each stage has its own reasoning budget. Sorting needs less reasoning than writing a script.

```ts
// One narration beat, as the writer model returns it
type Beat = {
  adds: string;        // what new information this line brings; checked, then thrown away
  contentText: string; // the narration itself
};
```

Asking the model to identify new information first helps reduce repetition.

<span id="be-precise-about-what-a-check-proves" aria-hidden="true"></span>

## Know what automated checks can prove

The system scores drafts and gives failed drafts specific feedback. A model reviews and rewrites them. Its revision must pass the checks and score higher to replace the original.

<div class="post-split not-prose">
  <div class="card post-yes fx">
    <p class="post-split-label"><Icon name="ph:check-circle" aria-hidden="true" /> Checked or enforced</p>
    <ul>
      <li>The script stays on its subject</li>
      <li>The opening follows the required structure</li>
      <li>Length and endings meet the requirements</li>
      <li>Later stages keep the approved narration or restore the checked version</li>
      <li>On-screen scores, standings, and prices come from data sources, not from the model</li>
    </ul>
  </div>
  <div class="card post-no fx" style="--d:70ms">
    <p class="post-split-label"><Icon name="ph:warning-circle" aria-hidden="true" /> Limits of these checks</p>
    <ul>
      <li><strong>That a claim is true.</strong> A false sentence built from words in the source can still pass.</li>
      <li><strong>Numbers in the narration.</strong> They are not checked.</li>
      <li><strong>Non-Latin scripts.</strong> They skip the subject check.</li>
    </ul>
  </div>
</div>

## Monitor backup providers

External API calls use shared logic for retries, API key rotation, and switching to a backup provider. Each task defines what the backup must preserve.

<div class="post-split not-prose">
  <div class="card post-rules fx">
    <p class="eyebrow">When a call fails</p>
    <ul>
      <li><span class="post-trigger">Temporary error</span><Icon name="px-arrow-right" aria-hidden="true" /><span>A few retries with longer delays between attempts</span></li>
      <li><span class="post-trigger">2 timeouts in a row</span><Icon name="px-arrow-right" aria-hidden="true" /><span>Switch provider</span></li>
      <li><span class="post-trigger">Empty balance</span><Icon name="px-arrow-right" aria-hidden="true" /><span>Pause calls to that provider for 30 minutes</span></li>
    </ul>
  </div>
  <div class="card post-rules fx" style="--d:70ms">
    <p class="eyebrow">What the backup must preserve</p>
    <ul>
      <li><span class="post-trigger">Voice</span><Icon name="px-arrow-right" aria-hidden="true" /><span>The same speaker</span></li>
      <li><span class="post-trigger">Images</span><Icon name="px-arrow-right" aria-hidden="true" /><span>The same quality level</span></li>
      <li><span class="post-trigger">Embeddings</span><Icon name="px-arrow-right" aria-hidden="true" /><span>Keep providers separate; their outputs are not comparable</span></li>
    </ul>

Videos kept finishing, so a provider failure went unnoticed for weeks.

## Track costs and know what is missing

I record paid API calls before checking their output, because unusable answers still cost money. Each record keeps the rate charged at the time. Failed or replaced attempts stay in the cost history.

## Postmortem: a syntax error in production

I decide what to build, how to structure it, and what to charge. Coding agents help write the code, which I review. On September 2, a faulty change reached production.

<aside class="post-incident card not-prose fx">
  <div class="post-incident-head">
    <span class="post-icon"><Icon name="ph:bug" aria-hidden="true" /></span>
    <div>
      <p class="eyebrow">Production incident · September 2, 2026</p>
      <p class="post-incident-title">One bulk edit, 18 hours of failed jobs</p>
    </div>
  </div>
  <ol class="post-timeline">
    <li><b>Cause:</b> an agent's bulk edit put code above the PHP opening tag. The tests that ran never loaded that file.</li>
    <li class="is-hit"><b>Impact:</b> scene-asset jobs failed for about 18 hours. Three videos stalled, and all three recovered after the fix.</li>
    <li><b>Detection:</b> a reviewer reported the problem by email before monitoring detected it.</li>
  </ol>
  <div class="post-incident-foot">
    <p class="eyebrow">Checks added</p>
    <ol class="post-fix">
      <li>A syntax check for every PHP file.</li>
      <li>A deployment check that stops before database changes if PHP syntax is invalid.</li>
      <li>A second review before merging.</li>
    </ol>
    <p class="post-incident-lesson">These checks target the failure that caused this incident.</p>
  </div>
</aside>

<dl class="post-figures not-prose">
  <div class="fx"><dt>~1,300</dt><dd>test definitions; the count does not prove the software is bug-free</dd></div>
</dl>

Next time, I would add syntax checks and basic smoke tests from the start. Tests need to cover likely failures, and monitoring needs to catch what tests miss.
