## Persist progress where recovery matters

Every stage saves its status in the database, so a failure resumes where it stopped instead of paying for the same generation twice. Voice and visuals run in parallel, then meet again at rendering.

One measurement corrected me. Starting each stage the moment the previous one finished fixed the median, not the whole delay.

  <div class="fx" style="--d:70ms"><dt>~1 min</dt><dd>Slowest waits, unchanged</dd></div>

<div class="decision-note not-prose">
  <p class="eyebrow">When I skip it</p>
  <p>This adds state and recovery paths to maintain. For the short, fixed sequence after a user edits a scene, a simple job chain is still the better choice. The full machinery is for generation that runs unattended and publishes in public.</p>
</div>

## Give models a structure, then check the result

Outputs are structured and checked against schemas. Each stage gets its own thinking budget: simple sorting does not need the budget of scriptwriting.

```ts
// One narration beat, as the writer model returns it
type Beat = {
  adds: string;        // what new information this line brings; checked, then thrown away
  contentText: string; // the narration itself
};
```

Naming the new information before writing the line pushes the model to say something new every time.

Simpler instructions helped, but prompts alone still let some bad output through. That is what the gates are for.

## Be precise about what a check proves

The system ranks drafts by their defects and tells a failed attempt exactly what to fix. A critic's rewrite wins only if it also passes the gates and scores higher.

<div class="post-split not-prose">
  <div class="card post-yes fx">
    <p class="post-split-label"><Icon name="ph:check-circle" /> Checked or enforced</p>
    <ul>
      <li>The script stays on its subject</li>
      <li>The hook has the right shape</li>
      <li>Length and endings fit</li>
      <li>Later stages keep the approved narration, or fall back to the checked lines</li>
      <li>On-screen scores, standings and prices come from data sources, not from the model</li>
    </ul>
  </div>
  <div class="card post-no fx" style="--d:70ms">
    <p class="post-split-label"><Icon name="ph:warning-circle" /> Not proven</p>
    <ul>
      <li><strong>That a claim is true.</strong> A false sentence built from words in the source can still pass.</li>
      <li><strong>Spoken figures.</strong> They are not checked.</li>
      <li><strong>Non-Latin scripts.</strong> They skip the subject check.</li>
    </ul>
  </div>
</div>

## Monitor the fallback path

External calls share one mechanism for retries, key rotation and switching providers. Each task also has its own rule for what a fallback must keep.

<div class="post-split not-prose">
  <div class="card post-rules fx">
    <p class="eyebrow">When a call fails</p>
    <ul>
      <li><span class="post-trigger">Temporary error</span><Icon name="ph:arrow-right" /><span>A few retries with growing delays</span></li>
      <li><span class="post-trigger">2 timeouts in a row</span><Icon name="ph:arrow-right" /><span>Switch provider</span></li>
      <li><span class="post-trigger">Empty balance</span><Icon name="ph:arrow-right" /><span>Shared 30-minute cooldown</span></li>
    </ul>
  </div>
  <div class="card post-rules fx" style="--d:70ms">
    <p class="eyebrow">What a fallback must keep</p>
    <ul>
      <li><span class="post-trigger">Voice</span><Icon name="ph:arrow-right" /><span>The same speaker</span></li>
      <li><span class="post-trigger">Images</span><Icon name="ph:arrow-right" /><span>The same quality level</span></li>
      <li><span class="post-trigger">Embeddings</span><Icon name="ph:arrow-right" /><span>Never mixed: their outputs do not compare</span></li>

## Record costs and understand the omissions

Billable calls are recorded before the output is validated, because an unusable answer can still cost money. Each entry keeps the rate that applied at the time, and replaced attempts keep their cost rows.

My session records include corrections to both code and business proposals, down to which features belong in paid plans. Agents still make mistakes that reach production.

<aside class="post-incident card not-prose fx">
  <div class="post-incident-head">
    <span class="post-icon"><Icon name="ph:bug" /></span>
    <div>
      <p class="eyebrow">Production incident · 2 September 2026</p>
      <p class="post-incident-title">One bulk edit, eighteen hours of failed jobs</p>
    </div>
  </div>
  <ol class="post-timeline">
    <li>An agent's bulk edit put code above the PHP opening tag.</li>
    <li>The tests it chose never loaded that file. The change merged and deployed.</li>
    <li class="is-hit"><b>Scene-asset jobs failed for about eighteen hours.</b> Three videos stalled.</li>
    <li>A reviewer's email surfaced the problem before my monitoring did.</li>
    <li>After the fix, the three videos recovered.</li>
  </ol>
  <div class="post-incident-foot">
    <p class="eyebrow">Safeguards added</p>
    <ol class="post-fix">
      <li>A test that every PHP file parses.</li>
      <li>A deploy step that stops before database changes if syntax is broken.</li>
      <li>A second review before merges.</li>
    </ol>
    <p class="post-incident-lesson">Those are real safeguards. Asking a tool to be more careful is not.</p>
  </div>
</aside>

Next time I would keep a small syntax-and-smoke check from day one. The useful question is which failure paths are checked, and what happens when a check misses.
